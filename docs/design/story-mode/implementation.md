## 3. 时长：模型不等于实测

`tests/yuye-duration.mjs` 用三档阅读速度估算**必经内容**的时长：

| 档位                                 |  阅读速度 |                     合计 |
| ------------------------------------ | --------: | -----------------------: |
| 保守下界（快读，但仍听完曲目与过场） | 600 字/分 |  约 407 分钟（6.8 小时） |
| 常规首见                             | 400 字/分 |  约 580 分钟（9.7 小时） |
| 沉浸细读                             | 300 字/分 | 约 746 分钟（12.4 小时） |

**这些是估算，不是首见实测。** 统计口径是「必经正文汉字 ÷ 阅读速度 + 地图停留 + 逐拍点击 + 谜题 + 完整曲目 + 完整过场 + 选择」，已排除支线、其他结局重玩、下载等待与挂机。真实首见时长必须由未读剧本的测试者用游戏内「记录」页的有效计时记录。

模型里 1,406 拍对白每拍都要点一次「继续」，这属于操作成本（快读者 1.2 秒/拍、常规 2 秒/拍），不是阅读也不是等待，因此单独计入而不是塞进阅读速度。

**目前写出来的是「6 小时以上」，但可能超出原设计的 6–8 小时上限。** 常规首见估算 9.7 小时，比设计目标长 1.7 小时。这不是把内容灌水造成的：正文是逐场景的真实对话，没有模板复读（`pnpm test:story` 会检查重复长句）。如果实测确认偏长，正确的修法是精修冗余段落与合并重复的日常互动，而不是提高难度或加强制内容；但如果实测确认玩家享受这种体量，也可以按现状保留，把「6–8 小时」更新为「7–10 小时」。这个取舍需要你的意见。

## 5. 尚未验证 / 需要外部条件

- **逐首真机演奏**：自动走查只验证了桥接、回执与剧情推进，没有逐首在引擎内确认谱面结束时间、BGA、附加资源与音画同步。
- **首见时长**：尚无未读剧本的测试者数据，`tracks.md` 的媒体时长只是上限，不等于引擎内时长。
- **已发布的冻结线索提交**：`story-evidence/` 已在本仓库内，但没有配置真实的 40 位 `VITE_STORY_ARCHIVE_REVISION`，因此谜题面板明确显示「尚未发布的源码线索」，只提供站内同版镜像，不伪造 SHA，也不把 `main` 当作冻结版本。发布时应以真实提交填该变量后重建。
- **PWA / 离线**：开发模式没有 Service Worker；离线行为需 `pnpm build && pnpm preview` 并实际断网验证。
- **跨标签页冲突**：已在真实双标签下复现并验证：A 写盘后 B 的写入被拒绝并提示「存档冲突」，磁盘内容保持 A 的版本；B 重新载入（或刷新）后可正常写入。同时修掉了两个导致该流程失效的缺陷（见下节）。
- **音频表现**：远端音频的 CORS 与可用性依赖部署环境，已在 `tracks.md` 记录 HEAD/ffprobe 结果，但没有承诺所有节点一致。

## 6. 与设计稿的差异

- 设计稿写「9 区域、45 个调查场景」；实现是 9 个区域、**50 个场景实例**（每章 5 个，第 9 章复用白页站与版心街的 5 个地点编号）。区域数不变，场景更多，因为第 9 章的复访需要独立状态。
- 原设计「每章 2 个有意义选择」；实现中有 6 章给了 3–5 个，第 1 章的 `bridge-name` 分支（`original` / `annotated`）保持在原位。
- 第 0/1/6/7/8/9 章的主线场景把 3 个调查物件全部设为必须调查。原因：这些物件各自带独立叙述与证据，只标 h0 会让另外两个看起来像装饰；设为必修后，收尾前必须逐件检查，不会漏证据。

## 7. 手工验收清单

1. `pnpm dev` → `/story`：开场 → 进入折页城 → c0s0 读完三处调查 → 选择 → 场景完成。
2. c0s1 打开证据板 → 空提交应提示缺项 → 三级提示可读 → 正确提交后回到剧情并自动推进。
3. c0s2 曲目：分别试手动、自动伴奏、纯聆听；三种都应能回到剧情，且记录页只显示回执、不写成绩。
4. 设置页：改文字倍率/降低动态应立即生效；导出 JSON 后重新导入应提示替换并保留进度。
5. 谜题 P03：「保存书签并重新开页」应在保存成功后真正刷新，回来后显示已重返；存储失败时「重开布景（不刷新）」仍可完成。
6. 手机竖屏：工具栏横向可滚动、对话框不被截断、谜题单选可点、无横向溢出。
7. 结局：第 9 章四个必经场景完成后进入离场协商，三种运行方式都能到达并回到后日谈。

已在生产构建（静态托管，非 `vite preview`）上自动跑过第 5 项的完整路径：保存 → 真实 `location.reload()` → 重新载入 → 面板显示「已确认重返」→ 提交 P03 通过，控制台无错误。

## 8. 已知的小问题

- 过场播放器在深色背景上有一层浅色描边盒子，与整体黑白色调不完全统一；不影响可读性与操作。
- 手机端隐藏了左侧调查侧栏，只能通过工具栏「调查」抽屉进入；这是为了避免窄屏挤压对话框，但首次进入会多一次点击。
- 自动走查用「纯聆听 + 跳过」推进 32 首曲目，因此回执模式多为 `summary`；这符合设计（跳过的部分不计完整聆听），但不能代替真实演奏的表现验收。
- 自动走查的计时数字偏低（对话约 18 分钟、音乐 0），因为脚本以极高速度点击、几乎没有真实阅读停顿，且一律跳过音乐。**这些数字不能当作用户时长**，只用于验证「会记录、不串类、不重复」。

## 9. 本轮修掉的跨标签与计时缺陷

这四个缺陷都是自动化走查发现的，不是自查发现的。它们共同的特点是：单标签一切正常，只有真实并发或真实播放时才暴露。

1. **活动计时每 5 秒推进一次 `revision`。** 另一个标签页无论怎么「重新载入」，都会立刻再落后一步，永远无法保存。改为计时只并入内存、不单独写盘；只在真正有进度变更时落盘。
2. **`patch()` 每改一个字符就自增 `revision`。** 在笔记框里打字会让版本号飞涨（实测从 11 跳到 27），也让冲突判定更容易被误触发。改为 `revision` 只在 `persist()` 真正落盘时自增一次。
3. **`onTrackComplete` 里的 `buffer.music = 0` 丢弃了未满 5 秒的播放时间。** 改为先 `flushTime()`；`cancelPerformance` 同样保留已发生的有效播放。
4. **逐拍对白每拍都即时落盘。** 1,400 拍对白会产生上千次写入，`revision` 无意义暴涨，也让另一标签页几乎永远处于「刚落后」状态。改为逐拍只标脏并延迟合并写入，进入场景 / 调查 / 曲目 / 谜题 / 过场 / 场景完成这些节点才即时保存；`persist()` 也加了并发保护（保存中再来的请求只记待写标记，完成后再写一次）。

另外两处可读性修正：`formatMinutes` 不足一分钟显示秒（18 秒不再显示成「0 分钟」），提示条改到右上角避免遮住底部对话框。实测 3 拍合并为 1 次写入。

## 10. 内容版本与协作纪律

`CONTENT_VERSION = 'yuye-1'` 与 `StorySave.contentVersion` 绑定。改动存档结构（字段增删、语义变化）必须同步提升版本号，否则旧档会被 `storage.ts` 明确拒绝载入。这是有意的：宁可报错并保留旧档，也不要静默地错读进度。

正文 JSON 是并行任务的高冲突区。约定：

- 只改自己负责的章节文件，不碰 `types.ts`、`model.ts`、`storage.ts`。
- 任何任务都不应对工作树执行 `git checkout` / `restore` / `reset` / `stash` / `clean`。这些命令会回退其他并行任务已写入、尚未提交的内容。查看状态只用 `git status`、`git diff`、`git show`。
- 核对字数只用 `node -e` 读文件统计，不要为了核对而重写文件。

本轮确实发生过一次事故：一个并行任务为重置自己的插入脚本，对 `chapter-06.json`、`chapter-07.json` 执行了 `git checkout --`，把同批其他写入一并丢弃，事后需要重写。上面三条纪律即由此而来。
